## 当前权重基线

项目成员已确认使用已经下载的 OpenPI 官方 `pi05_base` 基础 checkpoint。锁定归档中的官方引用为：

```text
gs://openpi-assets/checkpoints/pi05_base
```

这项确认只锁定初始权重来源。当前 OpenPI 归档没有名为 `pi05_base` 的可直接运行 `TrainConfig`；示例配置会将 `pi05_base/params` 装入 Libero、ALOHA 或 DROID 等具体数据配置。Piper X 同样需要一个与实际 episode 契约一致的专用配置和 transforms，不能借用其他机器人的配置来解释输入输出。

第一阶段策略实验不做微调，目的是验证基础模型在 Piper X Isaac Sim 场景中的零微调表现。项目成员已确认该基线沿用锁定版本的 `Pi0Config(pi05=True)` 默认设置：模型内部 `action_dim=32`、`action_horizon=50`、`max_token_len=200`、离散 state 输入，并省略额外 `sample_kwargs`；当前 JAX `sample_actions` 因而使用默认 10 个采样步骤。这些解析后的值应进入实验 manifest，不能只记录“default”。

这仍不等于直接把 32 维模型输出提交给 Piper。Piper 的有效 state/action 字段必须通过该版本的 padding/transform 机制映射；官方 output transform 去除内部维度 padding 后，episode 记录完整 50 步有效 action chunk、模型内部 shape 和 transform 引用，不要求修改 OpenPI 推理核心以导出内部 padded tensor。Piper 数据生成的归一化统计属于输入输出接口校准，不更新模型权重；它必须与数据 schema 和 transform 绑定，不能借用 ALOHA、DROID 或旧 OpenVLA 的统计量。目标机还应在 manifest 中记录本地 checkpoint 路径、校验值和实际加载结果。

“原生性能”在本项目中指：使用未微调的 `pi05_base` 权重、上述默认模型/采样设置和预先锁定的 Piper 映射运行固定仿真实验。运行开始后不得根据结果修改 prompt、归一化、输出缩放、动作裁剪或 chunk 策略再归入同一基线；任何这种变化都创建新的 experiment config。Piper 映射是让模型与环境字段可通信的必要条件，其版本和处理结果必须随 episode 保存。

## 必须保留的 OpenPI 范式

- π0.5 输出 action chunk；执行侧不能在未确认的情况下把接口改成单步动作。
- robot-specific 输入应通过 OpenPI 的数据配置和 transform 显式映射。
- 模型内部 state/action 维度与 Piper 有效维度不是同一概念；应使用该 OpenPI 版本提供的 padding 机制，不手写一个不兼容的模型头。
- LeRobot 数据的 action sequence key 必须与数据集实际字段匹配。
- 训练与推理必须使用相互对应的输入变换、输出变换和归一化统计量。

当前归档中可作为实现依据的入口包括：

- `src/openpi/training/config.py`
- `src/openpi/transforms.py`
- `examples/libero/README.md`
- `examples/libero/main.py`
- `src/openpi/policies/libero_policy.py`

Libero 仅用于理解官方接入方式，不作为 Piper X 的数据或控制语义。

## Piper X 接入缺口

仓库目前没有经过验证的 Piper 数据配置、repack transform、输入 transform、输出 transform 或推理客户端。实现前必须从实际 episode 和 Isaac Sim 控制接口共同确认：

1. 两个图像字段到 π0.5 图像槽位的映射；
2. state 的顺序、单位、夹爪定义和有效维度；
3. action 的来源以及绝对或增量语义；
4. 训练时的 action horizon 与推理时 chunk 执行策略；
5. checkpoint、训练统计量与数据 schema 的绑定；
6. 输出动作的反归一化、裁剪和控制侧转换。

在这些问题确认前，不创建推测性的 Piper policy adapter，也不把当前代理 action 写成正式控制目标。

## 历史 OpenVLA 工作区的使用边界

项目成员确认，外部 `agx_ws` 是模型切换前的 OpenVLA 数采与实机推理实现，`agx_datacollect_ws` 是同一代数据管线的独立采集工作区。它们可作为 Piper X 关节名称、物理单位、CAN/ROS 反馈、末端控制命令、夹爪命令和旧数据来源的历史证据，但不构成 π0.5 的模型接口或运行依赖。

静态检查显示，该旧链路使用单路 RGB 和 prompt，输出单个七维末端增量 `[dx, dy, dz, droll, dpitch, dyaw, gripper]`，再转换为绝对 TCP 目标并发送给 `pyAgxArm.move_p()`。旧数据的 `q01/q99`、动作 tokenizer、单步触发方式、checkpoint 补丁和执行阈值均与 OpenVLA 实现绑定，不得直接迁移为 π0.5 配置。

旧对齐脚本还使用 `action[t] = tcp_pose[t] - tcp_pose[t-1]`，而旧推理端把输出当作从当前 TCP 向未来执行的增量。它能证明历史动作的顺序、单位和低层执行入口，但不能证明监督标签的时间方向适合 π0.5。Piper 数据转换必须显式修正或重建 forward action target，并保留转换前后的时间索引证据。

当前双相机 LeRobot 采集器的代理 action、历史 OpenVLA 末端增量，以及未来接入的主臂控制目标是三种不同来源。π0.5 的 checkpoint、归一化统计、Piper transform 和 Isaac Sim 执行语义必须绑定到最终确认的数据来源，并保留原生 action chunk。

## 最小验证顺序

1. 用真实数据样本验证字段、形状、dtype 和 transform 的可逆部分；
2. 对一个 batch 完成 OpenPI 数据加载与前向接口 smoke test；
3. 用固定 observation 验证推理输出 shape、有效维度和反变换；
4. 在 Isaac Sim 中以记录模式执行 action chunk，并检查坐标、单位和时序；
5. 完成一次可复现的闭环 episode 后，才把 Piper transform 标记为 Verified。
