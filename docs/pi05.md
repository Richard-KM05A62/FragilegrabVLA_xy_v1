## 当前权重基线

项目成员已确认使用已经下载的 OpenPI 官方 `pi05_base` 基础 checkpoint。锁定归档中的官方引用为：

```text
gs://openpi-assets/checkpoints/pi05_base
```

这项确认只锁定初始权重来源。当前 OpenPI 归档没有名为 `pi05_base` 的可直接运行 `TrainConfig`；示例配置会将 `pi05_base/params` 装入 Libero、ALOHA 或 DROID 等具体数据配置。Piper X 同样需要一个与实际 episode 契约一致的专用配置和 transforms，不能借用其他机器人的配置来解释输入输出。

微调前先在官方 PiPER-X + D435 与锁定 LIBERO-derived MuJoCo 场景中保留一个未微调 zero-shot 诊断基线；它用于验证数据链路、执行语义和失败模式，不是当前研究的终点。该基线沿用锁定版本的 `Pi0Config(pi05=True)` 默认设置：模型内部 `action_dim=32`、`action_horizon=50`、`max_token_len=200`、离散 state 输入，并省略额外 `sample_kwargs`；当前 JAX `sample_actions` 因而使用默认 10 个采样步骤。这些值已进入服务元数据和实验 manifest。

这仍不等于直接把 32 维模型输出提交给 Piper。Piper 的有效 state/action 字段必须通过该版本的 padding/transform 机制映射；官方 output transform 去除内部维度 padding 后，episode 记录完整 50 步有效 action chunk、模型内部 shape 和 transform 引用，不要求修改 OpenPI 推理核心以导出内部 padded tensor。Piper 数据生成的归一化统计属于输入输出接口校准，不更新模型权重；它必须与数据 schema 和 transform 绑定，不能借用 ALOHA、DROID 或旧 OpenVLA 的统计量。目标机还应在 manifest 中记录本地 checkpoint 路径、校验值和实际加载结果。

“原生性能”在本项目中指：使用未微调的 `pi05_base` 权重、上述默认模型/采样设置和预先锁定的 Piper 映射运行固定仿真实验。运行开始后不得根据结果修改 prompt、归一化、输出缩放、动作裁剪或 chunk 策略再归入同一基线；任何这种变化都创建新的 experiment config。Piper 映射是让模型与环境字段可通信的必要条件，其版本和处理结果必须随 episode 保存。

## 必须保留的 OpenPI 范式

- π0.5 输出 action chunk；执行侧不能在未确认的情况下把接口改成单步动作。
- robot-specific 输入应通过 OpenPI 的数据配置和 transform 显式映射。
- 模型内部 state/action 维度与 Piper 有效维度不是同一概念；应使用该 OpenPI 版本提供的 padding 机制，不手写一个不兼容的模型头。
- LeRobot 数据的 action sequence key 必须与数据集实际字段匹配。
- 训练与推理必须使用相互对应的输入变换、输出变换和归一化统计量。

当前归档中可作为实现依据的入口包括：

- `src/openpi/training/config.py`
- `src/openpi/transforms.py`
- `examples/libero/README.md`
- `examples/libero/main.py`
- `src/openpi/policies/libero_policy.py`

Libero 仅用于理解官方接入方式，不作为 Piper X 的数据或控制语义。

## Piper X v0.1 接入状态

仓库已实现独立 MuJoCo π0.5 路径。当前 `piper_x_joint_position_dual_rgb_v0.3` 契约将 PiPER-X 六轴关节角（rad）和对称指位置（张开时 `+0.05/-0.05 m`）映射为六轴关节角加归一化夹爪闭合度（`0=open, 1=closed`）；OpenPI 内部仍使用 32 维 padding 和原生 50-step chunk。服务端 transform 对前六轴使用 delta normalization，夹爪保持绝对闭合度；输出再还原为绝对关节目标。

已提供锁定 commit 的专用 OpenPI server、与该版本 msgpack 协议一致的客户端、不执行动作的单次 inference check，以及保留完整预测 chunk/仅执行前缀后重规划的闭环 runner。模型元数据、关节范围、单步变化、非有限数和契约不匹配都是拒绝条件，不做静默 clipping。

新契约强制 `norm_stats_id` 以 `piper_x_` 开头，server 还要求 provenance 中的 `contract_id` 和 `robot_model=piper_x` 完全匹配。`piper_x_mujoco_scripted_calibration_v0.1` 已允许 MuJoCo zero-shot 诊断执行，但它不是微调训练集 normalization；正式 PiPER-X stats 仍必须从实际进入 pilot 的全部示范重算。

当前微调的首要目标是 PiPER-X embodiment adaptation，不是易碎性评判或正式 benchmark。Normalization 使用实际进入该次微调的全部训练示范，并通过锁定 OpenPI 版本的数据加载和 transform 路径统计。在当前契约中，前六维 action 先转为相对当前 state 的 delta，夹爪维保持绝对 closure；然后再计算 `state` / `actions` 的 q01/q99 等统计。产物必须与 dataset version、transform id 和 checkpoint 绑定。当前从非微调数据产生的 scripted MuJoCo stats 仅用于接口校准和 zero-shot 调试。

## PiPER-X embodiment pilot 训练契约（Confirmed）

- Robot：PiPER-X 6DoF + gripper。
- Dataset：LeRobot；采样率与 simulator control loop 一致，首轮为 20 Hz。
- State：`[q1..q6, gripper]`，共七维。
- Dataset action：七维 absolute joint target `[q1..q6] + gripper [0,1]`。
- Images：`front RGB`；只在最终 inference 也提供腕部相机时才将 `wrist RGB` 纳入训练契约。训练和推理的相机角色必须一致。
- Prompt：每个 episode 保存一条真实 manipulation instruction。
- Initialization：OpenPI 官方 `pi05_base`。
- Model action dimension：保留 π0.5 默认内部维度和 padding 机制；dataset 有效 action 维度为 7。
- Fine-tuning action horizon：首轮候选为 10 或 16；项目默认 pilot 选 16（20 Hz 下为 0.8 s）。这是独立微调实验，不改写 `pi05_base` zero-shot 默认 horizon 50 的基线记录。
- Execution horizon：不与训练 action horizon 混同；在同一 checkpoint 上独立 sweep `5 / 7 / 10`。
- Normalization：主实验重新计算 Piper-X stats；Trossen stats 仅作 ablation，必须使用独立 experiment id。
- Training：首轮只训练 `10k–20k` steps pilot，不直接扩到 100k。
- Checkpoints：每 1k steps 保存；每 5k steps 永久保留。最终选取约 4–6 个 checkpoint 进入仿真 rollout 评估。
- Selection：checkpoint 依据 MuJoCo rollout 表现选择，training loss 只作诊断，不单独决定最终 checkpoint。

以下项目仍须随新证据继续确认（迁移 Isaac 时另行验证）：

1. 当前 MuJoCo 相机位姿与未来真机相机标定的跨域差异；
2. 当前七维仿真映射与真机反馈/命令的最终核对；
3. 已确认的 20 Hz、pilot action horizon 16 与 execution horizon sweep 5/7/10 在锁定 OpenPI 实现中的运行验证；
4. checkpoint、训练统计量与数据 schema 的绑定；
5. zero-shot 失败模式在更多 seed 和场景扰动下的重复性。

当前 adapter 只对锁定的 MuJoCo 契约成立，不得据此直接生成真机控制目标。

## 历史 OpenVLA 工作区的使用边界

项目成员确认，外部 `agx_ws` 是模型切换前的 OpenVLA 数采与实机推理实现，`agx_datacollect_ws` 是同一代数据管线的独立采集工作区。它们可作为 Piper X 关节名称、物理单位、CAN/ROS 反馈、末端控制命令、夹爪命令和旧数据来源的历史证据，但不构成 π0.5 的模型接口或运行依赖。

静态检查显示，该旧链路使用单路 RGB 和 prompt，输出单个七维末端增量 `[dx, dy, dz, droll, dpitch, dyaw, gripper]`，再转换为绝对 TCP 目标并发送给 `pyAgxArm.move_p()`。旧数据的 `q01/q99`、动作 tokenizer、单步触发方式、checkpoint 补丁和执行阈值均与 OpenVLA 实现绑定，不得直接迁移为 π0.5 配置。

旧对齐脚本还使用 `action[t] = tcp_pose[t] - tcp_pose[t-1]`，而旧推理端把输出当作从当前 TCP 向未来执行的增量。它能证明历史动作的顺序、单位和低层执行入口，但不能证明监督标签的时间方向适合 π0.5。Piper 数据转换必须显式修正或重建 forward action target，并保留转换前后的时间索引证据。

当前双相机 LeRobot 采集器的代理 action、当前 MuJoCo 脚本的七维绝对位置目标、历史 OpenVLA 末端增量，以及未来接入的主臂控制目标是四种不同来源。π0.5 的 checkpoint、归一化统计、Piper transform 和 MuJoCo / Isaac Sim 各自的执行语义必须绑定到最终确认的数据来源，并保留原生 action chunk。

## 最小验证顺序

1. 用真实数据样本验证字段、形状、dtype 和 transform 的可逆部分；
2. 对一个 batch 完成 OpenPI 数据加载与前向接口 smoke test；
3. 用固定 observation 验证推理输出 shape、有效维度和反变换；
4. 在 MuJoCo 中以记录模式执行 action chunk，并检查坐标、单位和时序；
5. 完成一次可复现的闭环 episode 后，才把 Piper transform 标记为 Verified。
